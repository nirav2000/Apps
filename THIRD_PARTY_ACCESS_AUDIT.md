# Third-Party Access & Dependency Audit

_Last updated: 24 September 2026_

This register records third-party services, libraries and automated systems that can access, execute within, render, receive data from, or otherwise interact with the Apps portfolio.

It is intentionally separate from vulnerability/incident notes. **Do not put secrets, credentials, recovery tokens, exploit details or private incident-response information in this public file.** Security-sensitive findings belong in the private security notes.

## Why this exists

A third party may affect an app in several different ways:

1. **Loaded library** — JavaScript/CSS/package code runs in the app.
2. **Remote API/service** — the app sends requests/data to an external service.
3. **Renderer/screenshot service** — a third party actually opens and executes the app.
4. **Crawler/bot/link preview** — a third party visits pages automatically.
5. **Hosting/infrastructure service** — traffic/data passes through it.
6. **Analytics/telemetry service** — activity data is intentionally sent to it.

These should be visible and reviewable rather than discovered accidentally.

## Required fields

For each third party record:

| Field | Meaning |
| --- | --- |
| Provider | Third party/company/service |
| Type | Library, API, renderer, crawler, hosting, analytics, etc. |
| Apps/files | Where it is used |
| Purpose | Why it exists |
| Access/data | What it can see or receive |
| Traffic classification | How App Monitor should label visits generated by it |
| Required? | Required / optional / legacy |
| Review action | Keep, replace, restrict, investigate |
| Last reviewed | Date |

## Current register

### Thum.io

| Field | Value |
| --- | --- |
| Provider | Thum.io |
| Type | External screenshot/rendering service |
| Apps/files | `Apps/js/data.js`; historic generated preview URLs may also appear in `Apps/apps-data.json` |
| Purpose | Generate visual preview images for GitHub Pages apps shown in the Apps dashboard |
| Access/data | Thum.io is given the public app URL and renders the page in an automated browser. The renderer can therefore receive the same public HTML/assets/JavaScript that any visitor to that public GitHub Pages URL can receive. Because JavaScript executes, it can also trigger App Monitor. |
| Traffic classification | `synthetic-preview`, source `apps-preview` when the request was generated by the Apps dashboard |
| Required? | Optional convenience feature |
| Review action | Keep for now, but explicitly identify preview renders instead of hiding them. Monitor whether another preview method would reduce third-party access. |
| Last reviewed | 24 September 2026 |

### Discovery example

On 24 September 2026, App Monitor showed unexplained House-preview sessions from North American/Microsoft-hosted IP addresses even though the app had not knowingly been opened or shared by the owner.

Repository inspection found:

- `Apps/js/data.js` defines `screenshotFromUrl()` using `https://image.thum.io/...`;
- the Apps dashboard uses that function to produce app-card screenshots;
- House-preview loads the shared App Monitor client;
- therefore a remote screenshot render can execute House-preview and legitimately appear as an App Monitor session.

This is the reference example for why automated traffic should be **classified, not silently removed**.

The Apps preview generator now adds:

`app_monitor_source=apps-preview`

to the rendered app URL. The shared App Monitor client records that as:

- traffic class: `synthetic-preview`
- traffic source: `apps-preview`

The event remains visible in the monitoring dataset.

## Traffic classification policy

App Monitor should not claim that a normal-looking browser is definitely a human.

Use these classes:

| Class | Meaning |
| --- | --- |
| `synthetic-preview` | Explicitly generated by one of our own preview/rendering workflows |
| `known-automation` | Recognisable crawler/bot/automation user-agent signal |
| `likely-automation` | Browser exposes automation/headless signals but is not explicitly identified |
| `browser-session` | JavaScript browser session with no automation signal detected; **not proof of a human** |
| `unknown` | Legacy/incomplete record or insufficient information |

### Evidence hierarchy

Use evidence in this order:

1. explicit first-party source marker;
2. known bot/renderer user-agent;
3. browser automation signal such as `navigator.webdriver`;
4. referrer/source metadata;
5. network/ASN/cloud-hosting context as supporting evidence only.

**Do not classify a visitor as a bot solely because its IP belongs to Microsoft, Google, AWS, Cloudflare, a VPN, a data centre or another cloud provider.**

## Audit process for every maintained app

For each app review:

- inspect HTML for remote `script`, `link`, iframe, image and API origins;
- inspect JavaScript for `fetch`, WebSocket, remote image/rendering and SDK endpoints;
- inspect `package.json`, import maps and lock files for third-party packages;
- inspect Firebase/Cloudflare/Google/AWS integrations;
- inspect service workers for external caching/fetches;
- inspect analytics/telemetry integrations;
- identify screenshot/rendering/link-preview services;
- identify CDN-hosted libraries;
- record what data is sent and whether user content can be included;
- record whether App Monitor should recognise traffic generated by the service;
- remove stale/unused dependencies where practical.

## Future automation

A portfolio audit tool should eventually scan repositories for:

- remote origins in HTML/JS/CSS;
- package dependencies;
- external API hostnames;
- analytics tags;
- iframe/embed origins;
- screenshot/render services;
- OAuth/auth providers;
- CDN libraries.

It should compare discovered dependencies with this register and flag:

- new unregistered third parties;
- dependencies no longer found in code;
- version changes;
- services with unknown purpose;
- apps using a third party that has not been reviewed recently.

## Security note

The existence of a third-party dependency is generally visible in public source code and can be recorded here.

Do **not** record:

- API keys that are not explicitly public client configuration;
- private tokens;
- authentication secrets;
- exploitable configuration mistakes;
- private security incident details.

Those belong in the private security register.
